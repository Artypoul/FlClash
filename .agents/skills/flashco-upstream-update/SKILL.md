# Flashco Upstream Update

Обновляй Flashco от донора с сохранением пользовательского поведения. Сохранённые строки настроек
сами по себе не доказывают совместимость: проверяй собранный конфиг ядра, выбор узлов и маршруты.

## Вход и режим

Прочитай [AGENTS.md](../../../AGENTS.md) и используй
[flashco-workflow](../flashco-workflow/SKILL.md) как основной маршрут через Superpowers.
Этот скилл добавляет контекст обновления, а не второй параллельный процесс разработки.

| Запрос | Результат и границы |
| --- | --- |
| «Какие обновления», «сравни», «чекап» | Чтение локального Git и GitHub; отчёт без изменений файлов, fetch, checkout, сборок и миграций. |
| «Составь план» | Проверенный план с этапами и условиями остановки; запись только запрошенного плана. |
| «Обнови», «перенеси исправления» | Реализация только названного диапазона после проектных проверок и согласования существенных решений. |

Разрешения на commit/push/PR, merge, публикацию, установку и работу с реальными данными проверяй
отдельно по текущим инструкциям пользователя. Сам вызов скилла их не выдаёт. Тесты выполняй на
синтетических данных; запуск приложения на компьютере — только по правилам SAFE_MODE проекта.

## Сначала зафиксируй сравнение

1. Определи корень текущего репозитория, dirty-файлы, актуальную базовую ветку Flashco и состояние PR.
   Уже слитый PR не используй как рабочую ветку для следующего обновления. Не меняй неизвестные dirty-файлы.
2. Проверь `git remote -v`, `.gitmodules`, общий коммит приложения и отдельно SHA `core/Clash.Meta`.
   Донор приложения — `chen08209/FlClash`; донор ядра и его ветка определяются `.gitmodules`.
   Во всех `gh`-командах указывай репозиторий явно: по умолчанию CLI форка может выбрать донора.
3. Через GitHub проверь опубликованный стабильный релиз и текущие SHA `main`/`dev`.
   Раздели: уже включено в Flashco / выпущено донором / только в разработке. Версия в pubspec не заменяет Git-сравнение.
4. Зафиксируй целевой SHA и источники. Стабильный релиз — рекомендуемая основа;
   перенос из `dev` требует явно названного диапазона и решения пользователя.
5. Прочитай реальные diff, миграции и вызывающий код. Составь таблицу:
   `изменение донора → локальное отличие → данные/контракт → адаптация → проверка → откат`.
   Перед изменениями данных обязательно прочитай [сохранение настроек](references/settings-preservation.md).

Не включай в обычное обновление донорские скиллы, их зеркала, инструкции агента, hooks и конфигурацию
агента. Их изменение требует отдельного конкретного разрешения; массовый merge не обходит это правило.

## Что остаётся Flashco

- Обновление уже установленного Flashco сохраняет его application/package/installer ID, каталоги данных,
  исполняемые файлы, имя службы и собственный источник обновлений. Это не новый технический ребрендинг.
- FlClash и Flashco остаются разными установками; перенос между ними — через экспорт/импорт.
  Импорт старого архива не должен возвращать донорские пути, helper endpoint или идентификатор установки.
- Контракт Helper разрешено менять вместе с совместимыми Dart/Rust/Core-компонентами;
  не закрепляй старую версию протокола ради формального совпадения настроек.
- Сохрани ведущий `mihomo` в subscription User-Agent, проверив текущий реальный fixture выбора формата.
  Не подменяй его брендом донора или другого клиента. Реальные URL/ключи подписок в тесты и отчёты не попадают.
- Российские DIRECT-правила из `lib/common/default_rules.dart` — редактируемые начальные данные.
  При обновлении сохраняй пользовательские изменения и удаления; не засеивай существующую установку заново.
- Сохрани SAFE_MODE, защиту запуска после сбоя и правила владения жизненным циклом Core.
  Для native/Core-части используй [core-platform](../core-platform/SKILL.md).

## Порядок разрешённой реализации

1. Сначала добавь fixtures старых форматов и тесты сохранения поведения. Для обнаруженной регрессии
   воспроизведи падение теста до исправления через `superpowers:test-driven-development`.
2. Переноси независимо проверяемыми этапами: защита Helper и desktop-исправления; нужные им версии
   инструментов/контракты; изменения ядра; совместимость данных и профилей; затем зависящий от них UI.
   Если зависимость требует другого порядка, покажи её в плане; не представляй один коммит донора как независимый патч.
3. Разрушительные изменения схемы разрешены только после проверенного восстановления и тестов
   эквивалентности. При несовместимом старом режиме останови этот этап и вынеси выбор Артёму;
   готовность других этапов не означает готовность всего обновления.
4. После изменения моделей запускай штатную генерацию. После каждого этапа выполняй покрывающие его
   проверки из `.agents/commands.md`; используй `superpowers:systematic-debugging` для сбоев.
5. Перед завершением — `superpowers:requesting-code-review`,
   `superpowers:verification-before-completion` и проектное саморевью.
   Новый HEAD опубликованного PR требует свежих CI и настроенного внешнего ревью.

## Что доказывает готовность

Привяжи результаты к проверенному HEAD и целевому SHA донора. Укажи по каждому этапу сохранённые
настройки, тесты переноса, тесты восстановления, платформенные сборки и ещё не проверенные сценарии.
Базовые проверки приложения: `flutter pub get`, форматирование, `flutter analyze --no-fatal-infos`
и затронутые `flutter test`; команды Core/Helper/Android бери из актуального проекта.
Успех unit-тестов не заменяет проверку обновления установки и восстановления на соответствующей платформе.

Для performance-патчей отдельно сравни отзывчивость UI и скорость сети. Контрольные сетевые замеры
используют тот же узел, режим VPN, ресурсы и параметры; плавный UI не доказывает ускорение xHTTP.

Итоговый отчёт: целевой диапазон, что перенесено/отложено, сохранение данных, выполненные проверки,
готовность восстановления и статус `ready` / `partial` / `blocked` / `unknown`.
Недоступные обязательные проверки и непереносимые настройки называй явно.
