# Client Updates Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Execution is not started; recommended: inline implementation with independent review of signing, workflow and installer before release.

**Goal:** Дать клиентам Android и Windows проверяемый способ обновить Flashco с сохранением подписки и настроек через GitHub Releases.

**Architecture:** Отдельный ручной workflow собирает общий APK и Windows x64 EXE/ZIP на проверенном теге, проверяет идентичность и подпись, затем создаёт только draft. Клиентский интерфейс проверки обновлений остаётся существующим. Windows-установщик прекращает опасное завершение процессов по имени и проверяет принадлежность Helper.

**Tech Stack:** Flutter 3.47.6, Go 1.27.1, существующие Rust toolchain-файлы, Android NDK r28c / JDK 17, Inno Setup, GitHub-hosted Ubuntu и Windows 2022.

**Spec:** [Проект решения](2026-10-17-client-updates-design.md). Предложение подготовлено по запросу плана; перед реализацией Артём проверяет оба документа и выбирает способ исполнения.

Редакция после второго прохода 17.10.2026. Изменены только два документа; задачи реализации ниже ещё не выполнялись.

## Global Constraints

- Только Android `com.follow.flashco` с постоянной подписью и Windows x64. У клиентов предыдущих Android APK нет: подтверждено Артёмом 17.10.2026.
- Windows GUID `2E1E050C-79CA-52FB-82C4-52FDC3F5D780`, `CompanyName=com.follow`, `ProductName=Flashco` сохраняются.
- Общие публичные сборки: `APP_ENV=stable`, пустой `BOOTSTRAP_SUBSCRIPTION_URL`, `SAFE_MODE` выключен; native hooks включены в jobs упаковки. Исключение только для изолированного metadata-job задачи 4, не выдающего бинарников. Личные ссылки/профили/архивы и ключи не входят в Git, логи и артефакты; ключ не сохраняется в кэшах runner.
- Используется исходный checkout, без worktree/копий/алиасов. Не менять скиллы, инструкции, hooks агента и память проекта в этой задаче планирования.
- Публичный выпуск не обновляет `.dev` Артёма поверх. Его перенос — только явная операция backup/restore после разрешения.
- Сборщик персональных установщиков, прямой загрузчик/установщик в приложении, сервер Mildred, магазины и автоматическое закрытие работающего VPN — вне этого этапа.
- Старый donor upload с Telegram/Homebrew/F-Droid не включать. Изменение release secrets/environment, ключей, commit/push/PR/tag/publish и действия на устройствах — только по соответствующему поручению, не от имени этого документа.

## Review Focus

1. Нет ключа или подставлен debug signer: никакого публичного APK; задача 1.
2. Номер сборки вырос, но видимая версия та же: релиз не проходит preflight, поскольку updater сравнивает видимую версию; задачи 1 и 4.
3. У клиента уже сохранена подписка и ручная тёмная тема/выключенный автозапуск: общая версия их сохраняет, не импортирует чужое; задача 5.
4. Активный VPN/другая Windows-копия/чужой Helper: установщик не завершает чужой процесс и не показывает ложный успех; задачи 3 и 5.
5. Частичная загрузка, повторный запуск или неизвестный результат GitHub-записи: published/latest не меняется, проверенный файл не перезаписывается вслепую; задача 4.

Клиентское уведомление также является обязательной проверкой задачи 5: заголовок, описание, кнопка «Скачать», выключенная автопроверка, ручная проверка и отсутствие ложного «последняя версия» при сетевой ошибке.

При разрешённом коммите включать только согласованные документы явным `git add -f -- <точные пути>`, не менять глобальное правило игнорирования. `tool/release.sh`, включая `--dry-run`, не является read-only проверкой; подготовку версии/changelog выполнять явными согласованными действиями без его скрытых изменений и восстановления checkout.

## Зависимости этапов

1 → 2 → 3 → 4 → 5. Задача 1 проверяет чистые функции, а не ещё отсутствующий workflow. Задача 2 готовит команды упаковки; весь активный workflow создаётся только в задаче 4 после защит установщика. Доступ к ключу и реальные устройства — отдельные входные условия, не причина объявить непройденную проверку успешной.

## Task 1: Контракт общего выпуска и подпись

**Files:** Create `tool/release_preflight.dart`, `test/tool/release_preflight_test.dart`; later consume in `release.yaml`.

**Interfaces:**
- `validateReleaseIdentity({required String tag, required String version, required int buildNumber}) → List<String>` — пустой список только при стабильном `vX.Y.Z`, совпадающей версии без `v` и положительном коде.
- `validatePublishedUpgrade({required String version, required int buildNumber, required String? publishedVersion, required int? publishedBuildNumber}) → List<String>` — значения возрастают относительно максимальной видимой версии и максимального кода всей опубликованной стабильной истории, не только latest. Оба published-поля отсутствуют только после успешного чтения полной пустой истории. Неполные сведения, 403/404 и ошибки сети блокируют этот gate, а не превращаются в первый релиз.
- `validatePublicBuildDefines(Map<String, Object?> defines) → List<String>` — stable, без непустой встроенной подписки и safe mode.
- `validateAndroidIdentity({required Map<String, Object?> metadata, required String expectedSignerSha256, required String version, required int buildNumber}) → List<String>` — проверка фактических package/signer/versions/ABI/debuggable/testOnly; metadata формируется из настоящего APK инструментами SDK.
- Metadata содержит обязательные `packageName: String`, `versionName: String`, `versionCode: int`, `signerSha256: String`, `abis: List<String>`, `debuggable: bool`, `testOnly: bool`; отсутствие поля — ошибка. Fingerprint нормализуется к нижнему hex без разделителей перед сравнением.
- CLI возвращает 0 при успешной проверке, ненулевой код и безопасные причины при отказе; не выводит credentials или ссылку подписки.

- [ ] Снять безопасные образцы `apkanalyzer`/`apksigner` с имеющегося `.dev` APK; он служит отрицательным образцом, не эталоном релизной подписи. Схему metadata зафиксировать из этих выводов, релизный положительный образец добавить после первой подписанной тестовой сборки.
- [ ] Написать красные тесты: несовпадающий tag/version, prerelease в стабильном потоке, неположительный код, непустая подписка, safe mode, `com.follow.flashco.dev`, неправильный сертификат, отсутствие нужного ABI, debuggable/testOnly.
- [ ] Выполнить `flutter test test/tool/release_preflight_test.dart`; подтвердить падение по отсутствующей реализации.
- [ ] Реализовать минимальные проверки без нового release/backend API. Монотонность версии и кода проверять относительно фактической опубликованной истории и её manifest, не только текущего `pubspec.yaml`. Новый собственный manifest использует schemaVersion 1 из проекта решения.
- [ ] После разрешения получить/создать постоянный Android-ключ, зафиксировать публичный fingerprint и проверить резервное восстановление. Сам ключ и пароли хранятся вне checkout; доступ к GitHub signing environment настраивается отдельно.
- [ ] Подготовить контракт отрицательных metadata-fixtures для отсутствующего ключа/подставленного debug signer. Реальные workflow-проверки отсутствующего секрета и `apksigner verify --print-certs` выполняются в задачах 2/4 после появления jobs; в этой задаче не выдавать их за уже пройденные.
- [ ] Повторить тесты до PASS. При поручении на commit включить только файлы этой задачи; рабочая реализация проходит review до следующей зависимой задачи.

**Deliverable:** Формализованный и протестированный контракт; публичный канал не может выдать `.dev` или APK с чужой подписью.

## Task 3: Безопасная подготовка Windows-обновления

**Files:** Modify `windows/packaging/exe/inno_setup.iss`, `test/tool/packaging_config_test.dart`.

**Interfaces:** Сохранить `PrepareToInstall(var NeedsRestart: Boolean): String`, `CurStepChanged` и `InitializeUninstall(): Boolean`. Непустой результат подготовки означает отказ до копирования; отказ удаления возвращает false. Новые внутренние проверки: `HasRunningInstalledApp(): Boolean`, `HelperOwnershipConflict(): Boolean`, `StopInstalledHelper(var FailureMessage: String): Boolean`. Если статус/путь нельзя достоверно прочитать, проверка сообщает ошибку в обрабатывающий Prepare/Uninstall; неизвестное не приравнивается к false/отсутствию службы.

- [ ] Дополнить существующие source/config tests: GUID и runner CompanyName/ProductName не меняются; нет `/f /im` или другого глобального завершения по имени; подготовка обрабатывает отказ и сохраняет каталог пользовательских данных.
- [ ] Запустить `flutter test test/tool/packaging_config_test.dart`; подтвердить красный тест на текущем глобальном `taskkill`. Эти проверки не заменяют реальную установку в VM.
- [ ] Определять принадлежность процесса по полному нормализованному executable path в `{app}`, службы — по реальному SCM executable path. Прочитать контракт используемого Windows/Inno API перед реализацией; не считать одно имя службы доказательством владения. Зафиксировать проверку путей с пробелами и разным регистром.
- [ ] При активном приложении предлагать «Отключите VPN и выберите Выход в меню Flashco», затем повторить проверку. Не добавлять новый Core/IPC owner и не выполнять принудительную остановку чужого пути.
- [ ] Убирать/останавливать Helper только своей установки после штатного выхода; проверять код завершения и фактическое состояние. Применить те же ограничения в `InitializeUninstall`, который сейчас вызывает общие опасные функции. Отсутствие службы при чистой установке разрешено; ошибка SCM/чтения пути — отказ, а не «службы нет».
- [ ] Отделить отказ подготовки от сбоя `--clear-stale-proxy` после копирования: первый прекращает замену, второй сообщает частично завершённую установку и дальнейшее восстановление. Файловый rollback не считать восстановлением уже удалённой службы/прокси. Не обещать атомарный откат без VM-доказательства.
- [ ] Собрать EXE и проверить в изолированной Windows VM: активное приложение, другая копия, чужая служба, отказ UAC/SCM, неизвестный путь, отсутствующая служба, занятый файл, ошибка Helper, ошибка после копирования и нормальное обновление. Проверить и удаление своей установки с сохранением чужой копии. В основной пользовательской Windows приложение/VPN не останавливать.
- [ ] Повторить config tests до PASS; зафиксировать VM-доказательства. Реальное ошибочное завершение или зависание прокси блокирует выдачу Windows-файла.

**Deliverable:** Установка поверх закрытого приложения без глобальных kill и без ложного успеха при сбое подготовки.

## Task 4: Workflow и черновик релиза

**Files:** Create `.github/workflows/release.yaml`; Extend `tool/release_preflight.dart`, `test/tool/release_preflight_test.dart`; Add sanitized fixtures under `test/fixtures/release/` when parsing real API data.

**Interfaces:** `workflow_dispatch` с единственным обязательным `release_tag`. Preflight выдаёт полный `source_sha` и `release_version` как job outputs. Все jobs используют `checkout(ref: source_sha)`; тег повторно сверяется перед GitHub-записью. Входы передаются через env/структурированные аргументы, не вставляются в исполняемый shell-текст. Выпуски одного тега сериализуются через concurrency group, без отмены работающей загрузки. Выход — release ID и manifest того же tag/SHA, `draft=true`, `prerelease=false`, без изменения публичного latest.

- [ ] Снять реальные ответы `gh run list/view` и GitHub release API перед написанием их разбора; сохранить минимальные очищенные fixtures. Пустое состояние собственного репозитория тоже зафиксировать; для непустого контракта допустим реальный публичный ответ донора с последующей проверкой собственного draft. Выбрать последний запуск `build.yaml` именно выбранного SHA и подтвердить успешное завершение и все девять проверок: Dart, Plugins, Desktop linux/windows/macos, Go core, Android unit tests, Rust, Windows helper test. Новые queued/failed проверки не выдавать за зелёные и не заменять более ранним успехом.
- [ ] Добавить красные тесты для несовпадения tag/pubspec, отсутствующего/неосновного SHA, перемещения тега между jobs, незавершённого CI, отсутствующего секрета, неполного набора файлов, неверного хэша, уже published релиза и существующего draft от другого SHA. Максимумы версии/кода брать из полной опубликованной истории с пагинацией; 403/404 не считать пустой историей. Одинаковая видимая версия с другим build number отвергается.
- [ ] Реализовать preflight: workflow запускается из `refs/heads/main`, валидный стабильный тег, commit в истории main, согласованные pubspec/артефакты/CI; роль token по умолчанию read-only (`contents: read`, `actions: read`). Только job создания draft получает `contents: write`. Signing secrets доступны только проверенному исходному коммиту, без `pull_request_target` и запуска недоверенного кода.
- [ ] Учитывать hooks при запуске Dart CLI: metadata-job устанавливает Flutter и зависимости, временно отключает только оба native hooks в своей одноразовой копии и не выдаёт binaries. Jobs упаковки получают новый checkout `source_sha`, устанавливают полный набор инструментов задачи 2 и проверяют исходные `build_assets: true` до любой продуктовой сборки. Не выполнять root Dart preflight с отсутствующим Go/Rust и включёнными hooks.
- [ ] Создать защищённые build jobs из команд задачи 2. Проверить отсутствующий секрет до упаковки, debug signer по готовому APK и успех `apksigner verify --print-certs` с постоянным fingerprint. Данные подписи писать с корректным Java Properties-экранированием; секретный каталог не включать в кэши.
- [ ] Подготовить manifest schemaVersion 1 с `workflowRunId`: хэши/размеры только APK/EXE/ZIP. Затем `SHA256SUMS` для этих трёх файлов и manifest; не создавать циклический хэш manifest самого себя. Проверить отсутствие данных подписок/ключей/архивов; GitHub upload использует явный allowlist, а не старые локальные файлы из `dist`.
- [ ] Проверить changelog выбранного SHA/тега и получить body штатным `dart run tool/changelog.dart render release --tag vX.Y.Z --out release.md` в metadata-job. Уведомление клиента должно получить описание изменений из этого body. До внешней записи сохранить полный проверенный комплект и manifest как Actions artifact.
- [ ] В publisher-job с `contents: write` повторно прочитать опубликованные и draft releases и проверить совместимость API-доступа с выбранным target SHA. Read-only ответ preflight не доказывает отсутствие draft. Создать draft с release.md и APK/EXE/ZIP/manifest/checksums. Не включать старый donor upload, Telegram, Homebrew и F-Droid; latest не менять.
