# Обновления Flashco для клиентов: проект решения

Дата: 17.10.2026. Основание: `main`, `83089903cc33bbfb720af5e7ec37ba58cef5474e`.
Статус: предложение для проверки Артёмом; исправлено по второму проходу 17.10.2026. Этот документ описывает будущую реализацию; выпуск не выполнен.
Технические шаги: [план реализации](2026-10-17-client-updates-plan.md).

## Цель и подтверждённые решения

Клиент получает уведомление о новой версии, скачивает установщик и обновляет приложение с сохранением своей подписки и настроек. Для каждого обновления не требуется заново собирать персональное приложение.

Артём подтвердил 17.10.2026: предыдущие Android APK устанавливал только он; клиентам они ещё не раздавались. Поэтому первый клиентский Android-канал можно начать с постоянной подписи и `com.follow.flashco`. Отдельный канал обновлений тестовых APK клиентам не нужен.

Текущая задача — подготовка документов. Разрешены только эти два файла в `docs/plans/`. Код, скиллы, история/память, GitHub, ключи, серверы, установленные приложения и телефон не меняются. Выполнение плана, коммиты, PR и публикация потребуют соответствующего поручения.

## Варианты

| Вариант | Пользовательский путь | Объём |
| --- | --- | --- |
| **GitHub Releases, рекомендуется первым** | Уведомление → страница релиза → APK/EXE → системная установка | Использует готовую проверку обновлений; добавляются выпуск и проверки совместимости. |
| Загрузка из приложения | Уведомление → скачать нужный файл → предложить установку | Дополнительно нужны загрузчик, выбор платформы, проверка файла, отмена и работа с системным установщиком. |
| Магазины приложений | Обновления средствами магазина | Отдельные аккаунты, публикация и требования магазинов; текущая задача их не настраивает. |

Предлагается первый вариант. Он сохраняет текущий интерфейс; в первом релизе не добавляется Android-разрешение на установку пакетов. Дальнейший загрузчик можно спроектировать отдельно.

### Что видит клиент

- При запуске приложения выполняется одна автопроверка, если включена «Автопроверка обновлений». Закрытому приложению фоновые push-уведомления этот этап не добавляет.
- При более новой опубликованной версии открывается окно **«Доступна новая версия»**, номер, описание изменений и **«Скачать»**. Кнопка открывает страницу релиза; установку APK/EXE подтверждает пользователь.
- **«Больше не напоминать»** в текущем коде выключает автопроверку целиком, а не только уведомление об этой версии. Сохраняем существующее поведение; включить её можно в общих настройках. Ручная проверка в «О приложении» остаётся доступной.
- Ручная проверка текущей/более старой опубликованной версии сообщает **«У вас уже последняя версия»**. Ошибка доступа к GitHub не должна выдавать это сообщение вместо ошибки сети.
- Сейчас запрос запускается до запуска Core/VPN и не повторяется автоматически после появления сети. Если GitHub в этот момент недоступен, уведомление может не появиться; клиент может проверить вручную после подключения либо при следующем запуске. Автоматический повтор и новый расписанный опрос — отдельное изменение поведения, не скрытая часть этого плана.

Эти условия проверяются тестами задачи 5, включая отключённую автопроверку и работу VPN при ошибке сети. Подтверждены `lib/bootstrap.dart`, `lib/views/about.dart`, `lib/providers/actions/common.dart`, `arb/intl_ru.arb` и `lib/views/config/general.dart`.

## Предлагаемый выпуск

Этот порядок запускается после реализации задач 1–4, review и включения полного workflow в main. Пробные упаковки при разработке не считаются клиентским релизом.

1. В обычном PR подготовить версию и changelog; пройти проверки и review.
2. После разрешения выпуска создать стабильный тег `vX.Y.Z` на проверенном коммите `main`; дождаться CI тега, прежде чем запускать выпуск. Успех более раннего main-run не заменяет новую незавершённую/неуспешную проверку того же SHA.
3. В отдельном `release.yaml` запустить workflow вручную из `main`, указав тег. Один раз разрешить тег в полный commit SHA, проверить историю `main`, версию в `pubspec.yaml` этого SHA и CI именно этого SHA. Передать SHA всем последующим jobs и выполнять checkout по SHA, не по подвижному тегу. Перед созданием draft и публикацией повторно убедиться, что тег всё ещё указывает туда же.
4. Android собирается на `ubuntu-latest`, Windows x64 — на `windows-2022`. Переиспользуются Flutter `3.47.6`, Go `1.27.1`, NDK `r28c`, JDK `17` и текущие Rust toolchain-файлы. Для первого канала новые серверы и регистрация runner не нужны. Подключение Mildred можно согласовать отдельно.
5. Получить общий APK для трёх текущих ABI, Windows EXE и ZIP. Публичные сборки используют `APP_ENV=stable`, рабочий VPN и включённые native build hooks. Встроенная подписка пустая.
6. Проверить подпись, идентичность, версии, состав и SHA-256 файлов; сформировать сведения о коммите и сборке. Создать **только draft release** с явным списком этих файлов и `SHA256SUMS`, описанием из changelog выбранного тега. Существующий draft искать повторно в job с правом записи: read-only список может не показывать черновики.
7. Установить скачанные файлы B из draft на тестовые Android/Windows и проверить новую установку и обновление A → B. B не пересобирать для проверки. Использовать искусственную подписку без клиентских данных; проверяемый комплект привязать к хэшам.
8. После отдельного подтверждения Артёма опубликовать проверенный draft как стабильный latest. Только тогда существующая проверка обновлений должна предложить его клиентам.

Workflow сборки не получает личную ссылку подписки. Персональная первичная выдача приложения/подписки остаётся отдельным потоком; этот выпуск обновляет уже сохранённые профили и позволяет обычный первоначальный импорт. В тесте общей версии не должно появляться чужого профиля или автоматически перезаписываться ручное отключение/тема.

### Артефакты

- `Flashco-X.Y.Z-android.apk` — один APK с `armeabi-v7a`, `arm64-v8a`, `x86_64`; без выбора ABI клиентом.
- `Flashco-X.Y.Z-windows-amd64-setup.exe` — основной путь установки Windows.
- `Flashco-X.Y.Z-windows-amd64.zip` — отдельный ручной формат; не считать обновлением установки через EXE.
- `release-manifest.json` — `schemaVersion: 1`, `tag`, `commit`, `workflowRunId`, `version`, `buildNumber`, `android` (`packageName`, `signerSha256`, `abis`) и `assets` (только APK/EXE/ZIP: `name`, `size`, `sha256`). workflowRunId определяет исходный Actions artifact для восстановления загрузки. Хэш собственного manifest в него не включается.
- `SHA256SUMS` — контрольные суммы APK, EXE, ZIP и `release-manifest.json`; собственного хэша файла SHA256SUMS в нём нет. Секретных значений нет.

Видимая версия должна повышаться при каждом публичном обновлении, иначе нынешний updater его не обнаружит. Android `versionCode` также повышается. `v0.9.1` / `2026101701` — пример следующего выпуска, не созданный тег и не назначенная дата публикации. Окончательные значения проверяются по реальным тегам и уже опубликованным пакетам.

Пределы версии/кода берутся по всей доступной опубликованной стабильной истории, а не только по latest: latest могут переключить на более старый релиз. Подтверждение первого выпуска — успешное чтение полной истории без прежних стабильных релизов; один ответ 404, 403 или ошибка сети не доказывает отсутствие релизов. Опубликованные manifests и теги сохраняются; скрытие/удаление истории требует отдельного решения и сохранения прежних максимальных версий.

Для первого обновления A ещё нет у клиентов. Тестовую A собрать отдельно из проверенного `83089903cc33bbfb720af5e7ec37ba58cef5474e` (`0.9.0+2026101401`) с постоянной Android-подписью, `com.follow.flashco` и `APP_ENV=stable`; Windows — с тем же GUID. Это непубличная тестовая исходная установка, не новый release/tag и не замена существующего донорского тега. B — только проверенные загрузки draft с большими версией/кодом. В последующих выпусках A берётся из предыдущего опубликованного комплекта. Оба варианта фиксируются в журнале теста с SHA, подписью и хэшами.

### Порядок технических этапов

Сначала реализуются и проверяются контракты артефактов (задача 1), затем упаковка (2) и исправление установщика (3). Только после них собирается полный workflow (4); частичный workflow с доступом к signing secrets заранее не активируется. Проверка на устройствах и публикация — задача 5. Отсутствие ключа/телефона/VM не мешает подготовить код и тесты, но блокирует соответствующую реальную проверку и клиентскую выдачу.

Metadata-preflight на Dart запускается с учётом корневых native build hooks. В отдельном metadata-job допустимо временно выключить оба hook только в его одноразовой рабочей копии, как это делает существующий CI для служебных задач; этот job не собирает и не выдаёт приложение. Jobs упаковки получают свежий checkout по SHA и проверяют оба `build_assets: true` до сборки. Секретный ключ не должен попасть в кэши или artifacts.

### Постоянная подпись Android

До первой клиентской выдачи нужно получить или, после разрешения Артёма, создать постоянный ключ. Зафиксировать его публичный SHA-256 отпечаток, владельца и способ резервного восстановления. Закрытый ключ и пароли размещаются вне Git и передаются в защищённое окружение подписания GitHub; название предлагается `flashco-release`. Фактическое наличие секретов/защиты проверяется при настройке, значения в документы не записываются.

Контракт настройки: secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_STORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`; публичная variable `ANDROID_CERT_SHA256`. Названия предлагаемые, реальные значения в этом плане отсутствуют. Нужен доступ Артёма к восстановлению ключа вне GitHub; один CI-secret не заменяет резервную копию.

Публичный workflow прекращает сборку/выдачу при отсутствии данных подписи; готовый APK дополнительно проверяется на `com.follow.flashco` и одобренный сертификат. Существующий локальный fallback в Gradle не считается признаком готовности к выпуску и не должен пройти этот gate. На PR и непроверенные ref ключ не передаётся.

APK Артёма `com.follow.flashco.dev` — другое приложение. Постоянный выпуск не обновит его поверх. При желании Артёма: локальная резервная копия → установка постоянного пакета рядом → восстановление → проверка данных и нового VPN-разрешения. Удалять тестовую установку до проверки нельзя. Архив не загружается в GitHub.

### Безопасная установка Windows

GUID установщика, имя приложения, `CompanyName`, `ProductName` и каталог пользовательских данных сохраняются. Не добавлять удаление базы, preferences или профилей при обновлении.

Сейчас `inno_setup.iss` вызывает `taskkill /f /im` для трёх имён и игнорирует результаты удаления Helper и очистки прокси. Это может затронуть другую копию и обойти штатное сохранение настроек. Перед публичной выдачей нужен узкий фикс установщика:

- Первый сценарий: скачать EXE при работающем интернете, отключить VPN и выполнить **«Выход» из меню приложения**, затем запустить установщик. Закрытие окна может лишь свернуть приложение.
- Установщик обнаруживает активное приложение именно из `{app}` и предлагает штатно выйти; подготовка не продолжает замену работающих файлов. Нового IPC/команды удалённого закрытия в этот этап не добавлять.
- Глобальное завершение по имени убрать. Службой Helper можно управлять только после проверки её фактического executable path на принадлежность этой установке; чужой путь блокирует подготовку.
- Ошибка остановки/удаления нужной службы или замены файлов даёт понятный отказ. Повторная попытка выполняется после чтения фактического состояния, а не с заявлением об успехе.
- Отсутствующая служба при чистой установке — нормальный случай. Отказ доступа, неразрешённый путь процесса/службы и неизвестное состояние не считаются отсутствием: подготовка прекращается. Эти же ограничения распространяются на `InitializeUninstall`, вызывающий общие функции установщика.
- Проверить существующий `--clear-stale-proxy` и его результат. Отказ подготовки блокирует замену файлов. Ошибка очистки после копирования означает частично завершённую установку: сообщить о ней, сохранить журнал и дать восстановление/повторный запуск. Удаление службы и изменение прокси не считаются автоматически отменёнными откатом файлов Inno.

Логику Core и сохранения настроек оставить в существующих `SystemAction` / `SystemExitCoordinator`. Штатное обновление работающего VPN одной кнопкой — отдельное расширение.

## Границы и открытые проверки

- Постоянный ключ Android ещё не создан в этой задаче; доступ/резервирование согласуются до первой подписанной сборки.
- Подпись Windows Authenticode не настроена этим планом. Отсутствие предупреждения SmartScreen не является обещанным результатом. Покупка сертификата — отдельное решение.
- Известный Android-сценарий первого VPN-разрешения проверяется на телефоне. Если пользователь после разрешения вынужден повторно переключать кнопку, публичная выдача блокируется; само исправление оформляется отдельной задачей.
- Обновление со старых донорских/других package ID и миграции до v0.9.0 не входят в обещание сохранения данных. Для первого клиентского канала проверяется официальная версия A → B с одной идентичностью и подписью.
- Публикация черновика, окончательный release, изменение GitHub secrets/environment, создание ключа и действия на устройствах выполняются только в пределах соответствующего разрешения Артёма. План сам их не выполняет.
- `docs/` сейчас исключён из Git. При разрешённом коммите явно включать только согласованные документы через `git add -f -- <точные пути>`; общий `.gitignore` не менять ради этого плана. Скрипт `tool/release.sh --dry-run` не использовать для read-only проверки: он меняет файлы до проверки флага и выполняет восстановление через `git checkout`.
- Возможность создать draft штатным `GITHUB_TOKEN` проверяется для выбранного SHA. GitHub может дополнительно ограничивать выпуск, если target отличается файлами workflow от default branch. 403/404 не обходить расширением прав или новым PAT: сначала проверить исход и согласовать нужный способ доступа/переподготовки. [Условия GitHub Releases API](https://docs.github.com/en/rest/releases/releases#create-a-release).
- Сбой GitHub/интернета не блокирует основной запуск VPN. Ручная передача проверенного установщика остаётся возможной; новый сервер или зеркало этим планом не создаётся.

## Готовность результата

Готовым считается не успешное создание APK, а скачанный из draft и проверенный комплект: чистая установка и обновление A → B проходят на Android и Windows, профиль/URL/выбор/ручные настройки/правила сохраняются, VPN работает после установки и перезапуска, другой экземпляр Windows не остановлен. Все проверки относятся к точному SHA и хэшам файлов. Публикация согласована отдельно, после неё реальная старая официальная версия обнаруживает новый latest.

## Отказ и восстановление

До публикации сбой оставляет draft непубличным; нельзя выдавать частично собранный комплект. Повторный запуск не перезаписывает опубликованный релиз или файлы под тем же тегом. При неизвестном исходе загрузки сначала сверить release ID, tag/SHA, workflowRunId, список файлов и хэши; продолжать только из сохранённого Actions artifact исходного запуска, без пересборки. Если исходного комплекта больше нет, восстановление draft согласуется отдельно. Исправление кода после испытаний даёт новый SHA, новый тег/версию и новый комплект проверок; уже проверенный тег не переставлять.

После публикации исправление выпускается новой видимой версией и большим Android-кодом. Не обещать обычный downgrade APK с меньшим `versionCode` или восстановление новой схемы базы старой программой. Восстановление из резервной копии выполняется явно и сначала проверяется на тестовых данных.
